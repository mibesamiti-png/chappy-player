# Android本体更新：署名の競合を防ぐ

更新日: 2026-11-04。Xiaomi 11T Pro / Android 14 実機のフィードバックを反映。

## 実機で確認されたこと

- ARM64版APKのインストールに成功。
- サンプルメモ帳が表示され、日本語を入力できた（QA-03成功）。
- 別ビルドのAPKを既存アプリへ上書きしようとすると
  「パッケージが既存のパッケージと競合したため…」が表示された。
- 既存版をアンインストールした後はインストールに成功。
- QA-04（保存データが再起動後に残るか）およびQA-13（端末セルフチェック）は
  報告時点で未確認。

**署名が異なることが有力な原因だが、実機の署名フィンガープリント比較による確定は未実施。**

## 上書きインストールの条件

1. アプリケーションIDが同じ。
2. Androidが認める同一署名証明書または正当な署名鍵ローテーション履歴がある。
3. `versionCode` が同じか大きい（Chappy Playerは意図的に**大きい場合だけ**更新対象とする）。
4. Androidが要求する場合、ユーザーがインストールを承認する。

同じパッケージIDでも署名が違えば、上書きインストールは拒否される。
再インストールのためアンインストールすると、通常はアプリ内のデータも削除される。

GitHub Actionsの通常の`--debug` APKは、クラウドのジョブで生成される
**使い捨てデバッグ署名**である。別ジョブで上書きできるとは限らない。

## インストール前の署名確認

更新センターは、検証したAPKをAndroidのファイル保存画面へ送る前に
ネイティブ`PackageManager`を使って次を確認する。

- APKが読み込める
- インストール中のChappy PlayerとアプリIDが同じ
- `versionCode`が増えている
- 現在の署名証明書とAPKの実際の署名証明書が完全一致

失敗時は`SIGNATURE_MISMATCH`、`VERSION_NOT_NEWER`、
`PACKAGE_ID_MISMATCH`等の理由コードを出し、保存と更新を中断。
**アンインストールを自動実行しない。**

署名鍵ローテーションはこのMVPでは未対応（完全一致のみ許可）。
Androidのパッケージインストーラーが最終判断を行う。事前確認に成功しても
容量、権限、システム制限などでインストールできない場合はある。

## 固定署名へ移行する手順（これから）

1. **まず端末外へ`.chappybackup`を保存し、同じファイルから復元できることを実機で確認。**
   `.chappy`アプリ本体も別に保存。暗号化されていないバックアップに注意。
2. 端末の信頼できる環境でAndroid署名キーストアを1つ生成し、厳重にバックアップ。
   **鍵やパスワードをチャット、Issue、ソースコードに貼り付けない。**
3. リポジトリ設定の`Settings → Secrets and variables → Actions`に
   `CHAPPY_KEYSTORE_B64`、`CHAPPY_STORE_PASSWORD`、
   `CHAPPY_KEY_PASSWORD`、`CHAPPY_KEY_ALIAS`を登録。
4. 手動実行の`Build Signed Release APK`ワークフローを使用し、
   **同じ鍵**で署名したAPKを今後継続して配布する。
5. 現在の使い捨てデバッグ署名から最初のリリース署名へ切り替える時は、
   **旧アプリをアンインストールする必要がある可能性が高い**。
   バックアップから保存データを復元する。
6. 2つ目の固定署名リリースを`versionCode`増加でビルドし、
   旧アプリをアンインストールせず上書きできているかを実機で確認。
7. これが成功して初めて、更新センターからのAPK配布・自動検知を有効化する。

## 更新センターの現在地

- コードとFlutter自動テスト：実装
- 実端末向けARM64版の生成：GitHub Actionsで実施
- 公開可能な配布用HTTPS更新フィード：**未設定**
- Androidのインストール確認画面を更新センターから直接呼ぶ機能：**未実装**
- 署名事前照合：コード追加。CIとAndroid実機検証が必要
- 無人・無承認インストール：**実装しない**

**注意**：「更新センター画面がある」だけでは自動更新は動かない。
個人用の非公開GitHubリポジトリからの取得にAPIトークンをAPKへ
ハードコードすることは避ける。
