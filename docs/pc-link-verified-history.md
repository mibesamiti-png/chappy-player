# NETLAB-03B-5A — Android端末内・確認済みPC公開鍵の暗号化履歴

**状態：開発ソース・自動テスト対象。恒久ペアリングではない。正式APK未公開、Android/Windows実機での保存・復元テスト未実施。**

関連：[QR-v3の相互認証](pc-link-mutual-qr-v3.md) / [Issue #56](https://github.com/mibesamiti-png/chappy-player/issues/56)。

今回は**Androidスマホ側の確認記録**のみ。Windows側の信頼記録・ペアリング権限・再接続は変更しない。

## 今回追加したこと

- QR-v3でPCとAndroid双方の鍵所有証明が成功した後だけ、専用画面に「このPCの公開鍵を確認履歴に記録」ボタンを表示。QR-v2や指紋手入力だけの場合は出さない。
- 保存ボタンを押すと、保存するPC公開鍵SHA-256指紋と、操作権限は付与されないことを確認ダイアログに表示。「確認履歴だけ保存」を明示承認したときだけ記録。認証成功しただけでは自動保存しない。
- Network Lab →「PC連携用の端末キーを準備・削除」→「確認済みPCの記録を確認・削除」で、記録の一覧・保存日時・公開指紋の表示と、個別に確認を求める削除を提供。秘密鍵・IP・端末名は保存しない。
- Androidアプリ専用領域のJSONレコードをAndroidKeyStore管理のAES-256-GCM鍵で暗号化、AtomicFileで原子的に保存。最大24件・暗号化ファイル8KiB、記録の所有者が現在の端末P-256公開鍵と一致することを検証。
- Android本体のP-256端末キーを削除すると、確認履歴ファイルと履歴用のAES鍵も削除。再生成した端末IDでは過去記録を自動引き継ぎしない。

## セキュリティ上の境界

1. **これは接続権限を持つ信頼リストではない。** 記録しただけではPCへの操作、通信量取得、ファイル転送、自動再接続、バックグラウンド接続は不可。後続実装でも自動的に接続許可として流用しない。
2. Androidの履歴操作は前面の信頼済みFlutterホストだけから実行。記録時はWi-Fi/Ethernet条件も必要。.chappyミニアプリJavaScriptへ機能は公開しない。
3. 履歴用AES鍵はユーザーが明示保存したときだけ作成。履歴の一覧表示だけで鍵は作成しない。保存ファイルの破損・KeyStore鍵欠落・端末P-256指紋の不一致を黙って空記録として扱わず、エラーとして通知する。
4. WindowsでPC側の鍵を削除しても、Android内のローカル記録は同期して削除されない。この古い指紋を新たな接続許可に使ってはいけない。
5. 旧QR-v1/v2、ゲームサーバーHTTPS/WSS、ネットワーク探索、バックアップ、APK署名/版数、Stable配布系は変更しない。

## 検証と今後

- Flutterのテスト：読み込みのみで自動保存されない、公開情報の厳格な形式検証、重複拒否、削除ダイアログのキャンセル/承認を確認。
- Pythonのソース安全性テスト：AES-GCMとKeyStore、AtomicFile、保存制限、端末鍵削除時の履歴消去、ミニアプリJSの非公開、QR-v3成功後のみ保存ボタン表示の条件を確認。
- Android CIでFlutter analyze・test・Kotlinを含むDebug APKビルドを確認する。これと実機でのAndroidKeyStore、端末ロック、バックアップ復元、実際のPCとのWi-Fi接続は別。
- 次はWindows側にもDPAPIで暗号化した公開指紋記録と個別削除を実装。真正の恒久ペアリング・再接続・権限分離には、改めて双方の検証・失効制御・端末実機QAが必要。
- 正式署名APKは明示指示と実機QAなしに公開しない。
