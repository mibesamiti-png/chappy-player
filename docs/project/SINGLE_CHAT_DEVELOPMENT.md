# 単一チャット高速開発方式 v2 — Chappy Player

決定: 2026-11-08。**チャットを分けてABCD並行チームを作らない**。単一チャットで設計・実装・検証・統合・引き継ぎを完結する。会話が長くなったらGitHubのこの一式を読み直して再開。

## 役割分担と正本

- **GitHub**: 最新コード、最新HEAD、PR、CI実行結果、`docs/project/STATE.json`、ロードマップ、引き継ぎ、問題/実機記録。正本は常に実データ。
- **Notion**: 進捗と運用手順の人間向け要約・意思決定・リンク集。節目で明示的に更新する。**現時点で双方向/常時同期は実装していない**。
- **会話**: 次バッチの実装担当。ユーザーが「続けて」と言えば前回の未完了を復元し、可能な範囲で実装・テスト・PRまで進める。

## 速い1バッチの進め方（5〜10関連タスク）

1. **一度の読み込み**: 最新main HEAD、STATE、HANDOFF、ROADMAP、対象コード、関連テスト、直近PR/CIをまとめて取得。記載SHAを鵜呑みにしない。
2. **範囲を固定**: 既存機能への影響・安全境界・完了条件・実機が必要な項目を最初に分類。タスクの順序や細部はAIが自律設計してよい。
3. **実装準備**: 同一ソース/通信契約を共通化。可能ならローカル静的検査、構文/JSON/テスト事前チェック。WindowsとAndroidを別チャットには分けない。
4. **一括変更**: 関連ファイルはGit Tree API等で**1〜3コミットを目標**に一括更新。単一PRでCIを開始。無関係な巨大変更は分離。
5. **品質ゲート**: PRの**最終HEAD**に対しQuick CI成功。Windowsファイル変更時はWindows Companion Preview成功とEXE成果物確認。Androidプラットフォーム変更/実機節目はフルDebug APKビルドと実機QAを別管理。失敗は実ログから原因を特定し修正して再検証。
6. **統合**: 必須検証成功後にmainへ統合。mainのHEADを再取得。ブランチ競合や他者変更を無視してforce pushしない。
7. **引き継ぎ**: 節目でSTATE・HANDOFF・ROADMAPを実態に合わせ、Notionの冒頭に確定事項と次のタスクを反映。進行中作業も状態を明記して残す。
8. **スピード計測**: PR作成→統合時間、コミット数、CIやり直し回数、実機不具合件数を記録。短縮率は実測前に断言しない。

## 常に守る境界

- QR-v3相互署名は**一回限りの本人確認**。それだけでPC操作権・継続的なセッション・自動接続・ファイルアクセスを付与しない。
- 端末鍵・認証招待・秘密鍵・個人情報を公開GitHub、Notion、ログに保存しない。
- 既存のAndroid KeyStore / Windows DPAPI / TLS指紋固定・承認・権限分離を緩めない。
- 手動の鍵削除や履歴消去、データ破棄、署名Stableリリース、権限拡大を自動的に実行しない。
- CI成功≠APK生成成功≠実機PASS≠Stable公開。
- 公開ミニアプリのDebug/Stableは別リポジトリ。旧バージョンのバイナリを無断上書きしない。
- ユーザーの実機で確認できた事実以外、実機PASSにしない。

## 引き継ぎ時の整合性ルール

- `sourceMainAtCapture`は**記録時点の基準SHA**。現在HEADと一致しなくても即エラーにしない。差分を調べて状態記録を更新。
- PRがopenなら最新headでCIを見直す。PRがmergeされたらmain HEADとログで統合を確認。
- 未実装は `todo`、進行中は `in_progress`、完了は `done` と記録。承認・CI・実機のステータスは別欄。
- ユーザーが優先順位を変更したら、旧計画を消さず決定変更日と理由を追記する。
